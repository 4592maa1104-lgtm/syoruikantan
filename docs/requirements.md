# 建築業向け・音声業務管理アプリ 要件定義

（ユーザーから提示されたオリジナル要件。仕様判断で迷ったら必ずこのドキュメントを参照する）

## 1. このアプリを作る目的

建築業を営む一人親方が、現場から帰宅してパソコンの前に座り、見積書・請求書・領収書・経費・スケジュールなどの事務作業をまとめて処理する負担をなくす。

このアプリの最重要目的は、

**「パソコンに座る時間をできるだけなくし、スマートフォンだけで仕事の事務処理を完結できるようにすること」**

特に問題になっているのは「入力作業」。ユーザーは朝から晩まで現場と移動を繰り返しており、休みも不定期で月2〜3日程度働いている（原文ママ）。仕事量が多く、顧客・案件・協力してくれる仲間も多い一方で、見積書・請求書・領収書・経費・スケジュール・工程管理・顧客とのやり取りを基本的に一人で管理している。

そのため、**「情報を入力するための時間」そのものを減らすこと**を最優先にする。

## 2. 想定ユーザー

一人親方の建築業者。主な仕事は大工・リフォームだが、範囲は広く、大工・リフォーム・内装・建具関連・その他建築関連作業を扱う。完全な一人作業ではなく手伝ってくれる仲間もいる。下請け・元請け両方で仕事を受ける。顧客数・案件数も多く、一般的な「小規模一人親方向け」の単純な管理量を超えることを前提とする。

## 3. 最重要コンセプト：「入力するアプリ」ではなく「話しかけるアプリ」

ユーザーに大量のフォーム入力をさせない。基本操作は、

**話す → AIが理解する → 情報を整理する → ユーザーが確認 → 保存**

例：「8月20日9時から田中さんの○○邸。材料を買ってから現場に行く」→ AIが日付・時間・顧客・案件・内容・関連タスクを整理。ユーザーに一つ一つ入力させない。

## 4. ただしAIに勝手に確定させない

金額や顧客名の誤認識は重大な問題につながる。AIが推測した情報をそのまま正式な見積書・請求書として確定してはいけない。必ず、

**AIによる下書き → ユーザー確認 → 必要なら音声/タップで修正 → 正式確定**

特に金額・数量・単価・顧客名・日付・請求先・振込先・税額は確認しやすくする。

## 5. 中心データ構造

単純に「書類」を管理するのではなく、**顧客 → 案件 → 業務 → 書類 → 入金・経費** という関係を作る。

```
顧客
└ 案件
   ├ 予定・工程
   ├ 見積書
   ├ 請求書
   ├ 入金
   ├ レシート／領収書／経費
   ├ メモ／写真
   └ 関係者
```

これにより「○○邸の請求書どうなってる？」「○○邸はいくら請求した？」「○○邸の経費はいくら？」「田中さんからまだ入金されてない？」等に答えられる構造にする。

## 6. 見積書・請求書は最重要機能

ユーザーは既に決まった見積書・請求書フォーマット（現時点ではExcel形式の可能性が高い）を使用している。**新しいデザインの帳票を勝手に作らず、既存フォーマットをできるだけ維持する。** 実際のExcelテンプレートは後日提供される。テンプレート確認後、顧客名・住所・案件名・日付・明細・数量・単価・金額・小計・消費税・合計・振込先等を差し替えられる仕組みを作る。

## 7. 見積書作成を極限まで簡単にする

例：「田中工務店、○○邸のリフォーム、キッチン工事30万円、クロス12万円、諸経費5万円で見積作って」→ AIが整理 → 確認画面 → 「見積書を作成」で既存テンプレートに反映 → PDF（必要ならExcel）出力。

## 8. 請求書は見積書から作れるようにする

見積書 → 請求書をできるだけ自動で引き継ぐ。「○○邸の請求書作って」だけで過去の見積・案件情報を呼び出す。同じ内容の再入力は禁止に近いレベルで避ける。「見積と同じ内容で請求しますか？」→ はい、で作成。

## 9. 請求書ステータス管理

案件ごとに：見積未作成／見積作成済み／見積送付済み／受注／工事中／完了／請求書未作成／請求書作成済み／請求書送付済み／入金待ち／入金済み、を管理。ただし画面上に大量のステータスを並べて複雑にしない。「今、何が終わっていて、何が残っているか」を直感的に確認できるUIにする。

## 10. レシート・領収書・経費管理

スマホで撮影 → AIが読み取り → ユーザーが必要なら音声で補足 → 案件・経費に登録。例：「○○ホームセンター、12,800円。○○邸の材料」→ 店舗・金額・日付・案件・経費区分を整理。

## 11. レシートは「撮影しただけ」で終わらせる

「撮影 → 大量入力」をさせない。撮影後、AIが金額・店舗を読み取り「どの案件ですか？」等の最小限の確認のみで保存。

**注意：** 撮影したら紙を捨てていいという仕様は独断で実装しない。電子帳簿保存法等の要件が関係するため、税務上の扱いは別途確認する（未確定事項）。

## 12. スケジュール管理

手入力を極力なくす。「明日9時、○○邸。田中さんと2人」→ 日付・時間・案件・顧客・同行者を自動登録。**スケジュール単体ではなく案件と紐付ける。**

## 13. 顧客情報

一度登録した顧客情報（会社名・住所・担当者・電話・メール等）は何度も入力させない。「田中工務店の請求書」と言えば自動的に候補として出す。

## 14. 音声操作を最優先

スマホ利用が前提。車移動が多いため「片手で何回もタップ」より「短く話す」設計を優先する。**ただし運転中の操作を前提としたUIや運転中の注視を促す設計はしない。停車中・安全な場所での利用を前提とする。**

## 15. 入力方法の優先順位

1. 音声
2. 写真
3. 最小限のタップ
4. 必要な場合のみキーボード

レシート・領収書・既存書類・名刺・現場資料は写真から情報を取り込めるようにする。

## 16. 「みみより」との関係

既存の「みみより」アプリと完全に一つにする必要はない。ただしAIによる音声理解・情報整理の基盤は共通化できる設計にする。みみより＝タスク・予定・持ち物・提出物・日常情報。本アプリ＝案件・顧客・見積・請求・入金・経費・レシート・工程・業務スケジュール。**「共通AIエンジン＋用途別UI」という考え方だが、初期開発では無理に統合せず、本アプリ単体で成立することを優先する。**

## 17. UI設計の最重要ルール

対象ユーザーは業務管理アプリをほとんど使っていない。「多機能だから良い」ではなく**「何を押せばいいか一瞬で分かる」**ことを最優先する。ホーム画面には主要機能（🎙️話す／📄見積・請求／📸レシート／📅今日の予定 など）だけを分かりやすく配置する。

## 18. 「やらなくていいこと」を増やす

アプリの価値は機能数ではなく、今までユーザーがやっていた作業をどれだけ消せるかで判断する。顧客情報・案件名・金額の再入力、見積から請求書への再入力、Excelファイル探し、PDF作成、ファイル名を考える作業、レシートの後まとめ整理、スケジュール手入力などを減らす。

## 19. AIの役割

音声の理解／情報の分類／顧客名・案件名の候補認識／日付・時間の抽出／金額・数量・単価の抽出／レシート情報の読み取り／文章の要約／書類作成用データの整理／ユーザーからの質問への回答。**ただし金額や正式書類の確定は人間の確認を必須とする。**

## 20. セキュリティ・コスト

顧客情報・金額・請求情報・領収書などの重要データを扱うため、**APIキーをフロントエンドに直接埋め込む設計は禁止。** AI APIはサーバー側処理を経由させる。課金が発生し得る処理を勝手に増やさない。開発中は無料・低コストな方法を優先する。課金やセキュリティ上の重大リスクが発生する場合は実装を進めず、まずユーザーに確認する。

## 22. 開発フェーズ

- **Phase 1**: 音声入力 → AI整理 → 確認 → 保存
- **Phase 2**: 顧客・案件管理
- **Phase 3**: 見積書作成
- **Phase 4**: 見積 → 請求書
- **Phase 5**: レシート撮影 → 経費登録
- **Phase 6**: スケジュール・工程管理
- **Phase 7**: 入金管理・検索・分析・その他便利機能

いきなり全機能を完成させない。

## 23. 開発方針（重要）

「一般的な建築業務管理システム」として作らない。目的は**「一人親方が大量の事務作業をスマートフォンから、できるだけ喋るだけで処理できるようにすること」**。

「顧客を登録してください」→「案件を登録してください」→「明細を入力してください」→「金額を入力してください」のように大量のフォームを並べる設計は禁止。

「田中さんの○○邸、先月の見積と同じ内容で請求書作って」と言ったら、AIが過去データから候補を探し「田中工務店・○○邸の見積No.○○を元に請求書を作成しますか？」と確認するような設計を目指す。

## 24. 最終的に目指す体験

現場 → 車に戻る → スマホを開く → 話す → AIが整理 → 必要な部分だけ確認 → 保存 → 必要ならその場で見積・請求書作成 → PDF等で送付 → 完了。

**「帰宅してパソコンの前に座らない」** ことが最終的な成功基準。機能数ではなく、**「この人が一日の終わりにパソコンを開く回数をどれだけ減らせたか」**で評価する。
